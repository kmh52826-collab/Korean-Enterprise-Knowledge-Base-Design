# Validation Management Platform 데이터베이스 기술 구성 제안서

- 작성 기준일: **2026-09-18**
- Database 담당: **김민호**
- 설계 자료: [데이터 테이블 정의서](../data-dictionary.md), [회사별 Silo DB 검토안](./SILO_DB_ERD_REVIEW.md)
- 현재 사용 규모: 특정 업무 담당자가 사용하는 시스템으로, 이용자 수는 많지 않을 것으로 예상. 고객사 수·동시 접속자 수·데이터량은 별도 확인 필요

**PostgreSQL과 회사별 Silo 구성을 기본 전제로 한다. UTF8·UTC와 데이터 설계·변경 관리 원칙은 DB 담당 기준안으로 정리하고, AWS 서비스·세부 버전·배포 도구·백업·장애 대비는 관련 담당자와 확정한다. AWS 서비스는 RDS for PostgreSQL을 우선 검토하며, pgvector는 도입 검토 상태로 둔다.**

## 1. 개발 기술 구성표에 기재할 내용

| 구분 | 기재안 |
|---|---|
| 영역 | Database |
| 담당 | 김민호 |
| 언어 및 Runtime | **SQL / PostgreSQL 엔진** |
| Framework·DB | **PostgreSQL 사용, 회사별 Silo 구성. AWS 서비스는 RDS for PostgreSQL 우선 검토. pgvector 도입 검토 중** |
| 추가 항목 | **기준안:** UTF8 문자 저장, UTC 시간 저장, DB 변경 SQL·적용 이력 관리.<br>**협의 후 확정:** PostgreSQL 버전, Flyway 등 변경 관리 도구, pgvector·기타 확장 기능, 서버 사양, 백업 보관 기간, 장애 대비 구성 |

Runtime은 SQL을 실행하는 DB 엔진을 뜻한다. Flyway는 테이블·컬럼 변경을 적용하는 도구이며, pgvector는 벡터 검색을 위한 추가 기능이다. 두 도구의 사용 여부는 PostgreSQL 선정과 별도로 결정한다.

## 2. 김민호 담당자가 기준안으로 확정할 수 있는 항목

여기서 **‘90% 이상 확정 가능’은 현재 요구사항과 명세에 근거해 추가 제품 비교 없이 설계 기준안으로 정리할 수 있다는 의미**다. 실제 설정·개발·검증까지 완료되었다는 의미는 아니다. 이미 정해진 전제와 이번에 채택할 수 있는 기준을 구분한다.

| 항목 | 정리할 기준 | 판단 근거·현재 상태 |
|---|---|---|
| DB 종류·사용 언어 | **PostgreSQL / SQL** | 현재 협의에서 확인된 방향. 메이저·세부 버전은 별도 선정 |
| 고객사 데이터 분리 | **회사별 Silo** | 상사 지시로 정해진 전제. 고객사별 전용 DB 환경의 실제 구성은 인프라와 협의 |
| 문자 저장 방식 | **UTF8** | 한글·영문 등 다국어 저장 기준으로 채택 가능. 한글 정렬·검색 방식은 BE와 별도 확인 |
| 시간 저장·표시 기준 | **DB·연결 세션은 UTC, 화면은 사용자 또는 사업장 시간대** | 기존 데이터 테이블 정의서에 명시된 기준. BE·화면 담당자가 변환 방식을 맞춰 구현 |
| 날짜·시각 자료형 | 시점을 기록할 때 **timestamptz**, 날짜만 기록할 때 **date** | 기존 명세 유지. 승인 시각과 감사일 같은 날짜 필드의 용도를 구분 |
| 명명·자료형 기준 | **snake_case**, 기존 명세의 **UUID·JSONB 등 용도별 자료형 유지** | 현재 설계를 기준으로 진행 가능. 애플리케이션의 저장·조회 방식은 BE와 검증 |
| 데이터 관계·기록 보존 원칙 | PK·FK·UNIQUE·CHECK 사용, 승인 원문은 개정·이력으로 보존, 주요 변경은 감사기록에 기록 | 기존 명세의 설계 원칙 유지. 개별 제약과 업무 검증의 구현은 BE 공동 검토 |
| DB 변경 관리 원칙 | **변경 SQL을 Git에서 버전 관리하고, 회사별 DB에 적용한 이력을 기록** | 도구 선정 전에 정할 수 있는 원칙. Flyway 채택 여부는 별도 협의 |

문자·시간 기준은 PostgreSQL의 UTF8 지원 및 시간대 처리 방식과 일치한다. [PostgreSQL 문자셋](https://www.postgresql.org/docs/17/multibyte.html), [날짜·시간 타입](https://www.postgresql.org/docs/17/datatype-datetime.html)

현재 72개 업무 테이블은 설계·검토의 기준이다. 위 기준을 정한다고 모든 컬럼·인덱스의 검토가 끝나거나, 향후 물리 테이블 수가 72개로 고정되는 것은 아니다. AI 검색 저장 구조와 도구용 이력 테이블은 필요에 따라 별도 설계한다.

## 3. 인프라 담당자와 확인할 항목

**RDS for PostgreSQL을 우선 후보로 제안한다.** 제한된 인원이 사용하는 업무 시스템이고 현재 설계에서 Aurora 전용 기능이 반드시 필요한 요구는 확인되지 않았다는 점에 근거한 판단이다. 실제 성능·비용 비교를 마친 최종 선정은 아니다.

RDS for PostgreSQL은 자동 백업·시점 복구와 장애 대비 구성을 지원한다. 필요한 운영 조건을 먼저 정한 뒤 RDS와 Aurora의 비용을 같은 조건에서 비교한다. [AWS RDS for PostgreSQL 안내](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_PostgreSQL.html)

| 항목 | 현재 제안 | 확인할 내용 | 협의 대상 |
|---|---|---|---|
| **AWS DB 서비스** | **RDS for PostgreSQL 우선 검토**, Aurora는 비교 후보 | 회사별 Silo로 운영할 때 필요한 기능을 충족하는지, 회사당·전체 비용이 얼마인지 | 인프라·김민호 |
| **실제 AWS 지원 엔진·세부 버전** | PostgreSQL 사용. **17 계열은 검토 후보**, 최종 버전 미정 | 선택한 서비스·리전에서 제공하는 버전, 지원 기간, 드라이버·추가 기능 호환성 | 인프라·BE·김민호 |
| **고객사별 배치·리전** | 회사별 전용 DB 환경, 개발·검증·운영 환경 구분 | 전용 인스턴스 또는 클러스터 구성, 데이터 보관 지역, 신규 고객사 DB 생성 절차 | 인프라·BE·김민호 |
| **서버 사양·저장 용량** | 작은 규모부터 필요한 용량을 산정 | 회사 수, 동시 사용자, 문서·DB 데이터 증가량, 보고서·AI 검색 부하에 따른 사양과 비용 | 인프라·BE·AI |
| **Backup: 백업·복구** | 자동 백업과 특정 시점 복구 사용 제안. **보관 일수 미정** | 며칠 전까지 복구할지, 실제 복구 절차와 시험 주기, DB 밖의 첨부파일 복구 방법 | 인프라·김민호·업무 책임자 |
| **가용성: 장애 대비** | 운영 DB의 예비 서버를 두는 **Multi-AZ 구성 검토** | 서비스가 얼마나 멈춰도 되는지, 장애전환·재접속 방법과 추가 비용 | 인프라·BE·업무 책임자 |
| **접속·암호화** | 허용된 서버에서 접속, 저장·통신 암호화, 필요한 권한만 부여 | 접속 경로, DB 계정·암호 관리, 인증서와 암호화 키 관리 방식 | 인프라·BE·김민호 |
| **유지보수·관찰** | 버전 변경 전 검증, 장애·성능 이상 알림 | 업데이트 시기, 점검 시간, 알림 담당자, 로그 보관·조회 권한 | 인프라·BE·김민호 |

**사용자가 적다는 정보는 서버 용량을 산정할 때 활용한다. 백업과 장애 대비 수준은 업무 중요도 및 허용 중단시간을 기준으로 결정한다.**

백업 보관 기간은 오삭제·장애 복구를 위한 기간이다. 승인 문서·전자서명·감사기록을 보존해야 하는 기간은 업무 책임자와 별도로 정한다. RDS는 설정한 백업 보관 범위 내 시점 복구를 지원한다. [AWS 자동 백업·복구](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.html)

Multi-AZ는 여러 가용 영역에 걸쳐 장애에 대비하는 구성이다. RDS의 **주 서버 + 대기 서버 1대** 방식에서는 대기 서버를 일반 조회용으로 사용하지 않는다. 필요한 경우 조회용 복제본은 별도로 검토한다. [AWS Multi-AZ DB 인스턴스 설명](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html)

실제 지원 버전은 서비스·배포 리전 선정 후 확인하고 기록한다. [RDS PostgreSQL 버전 확인 기준](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.DBVersions.html)

## 4. BE·배포 담당자와 확인할 항목

BE는 데이터를 저장·조회하고 승인·시험 등의 업무를 처리하는 백엔드 담당자를 뜻한다. 김민호는 데이터 구조와 필요한 규칙을 제시하고, BE·배포 담당자는 이를 구현·배포할 방법을 함께 정한다.

| 항목 | 현재 제안 | 확인할 내용 | 협의 대상 |
|---|---|---|---|
| **Migration Tool: DB 변경 관리 도구** | **Flyway 우선 검토**. 팀에서 이미 사용하는 도구가 있으면 먼저 확인 | 기존 도구 유무, 필요한 기능, 배포 방식, 버전·라이선스 및 비용 | BE·배포·김민호 |
| **변경 SQL 작성·적용 역할** | DB 설계 변경을 SQL 파일로 관리하고 배포 과정에서 회사별 적용 | SQL 작성·검토·실행 담당, 적용 순서, 실패한 회사 DB 재처리 및 앱 버전 호환 방법 | BE·배포·김민호 |
| **PostgreSQL 연결 드라이버** | 백엔드 구성에 맞는 드라이버 사용 | Java·Spring Boot 등 실제 백엔드 버전과 선택한 PostgreSQL 버전의 호환성 | BE·김민호 |
| **문자·시간·자료형 연결** | UTF8·UTC 및 기존 명세의 자료형을 공통 기준으로 사용 | 한글 저장, 시간대 변환, UUID·JSONB 저장·조회, 한글·영문 정렬 규칙 | BE·화면 담당·김민호 |
| **회사별 DB 선택과 조직 소속** | 인증된 고객사 정보로 DB 선택. `organization_id`는 내부 조직 식별용으로 유지하는 안 제안 | 요청·배치·AI 작업에서 회사가 섞이지 않는지, 내부 조직·사업장 및 협업 범위가 업무와 맞는지 | BE·인프라·김민호, 조직 범위는 업무 담당 |
| **데이터 제약·동시 처리** | 기존 명세의 관계·승인·개정·감사 규칙 구현 | DB 제약과 서버 검증의 역할, 중복 승인·최신 개정 충돌 방지, 상태·서명·감사기록의 함께 저장 | BE·김민호 |

Flyway는 적용되지 않은 변경 파일을 순서대로 실행하고 DB별 이력을 관리하는 도구다. Silo 전용 또는 AWS 필수 구성품은 아니며, 사용 여부는 개발·배포 방식에 맞춰 결정한다. [Flyway 변경 적용·이력 관리](https://documentation.red-gate.com/flyway/flyway-concepts/migrations)

Flyway Community는 무료판으로 제공되지만, 팀의 실제 사용 방식과 필요한 기능을 확인한 후 에디션을 정한다. [Flyway Community 안내](https://www.red-gate.com/products/flyway/community/)

현재 14개 ERD SQL은 그림에 필요한 참조 테이블이 반복되고 일부 컬럼이 생략된 표시용 자료다. 운영 DB를 생성할 때는 [데이터 테이블 정의서](../data-dictionary.md)를 기준으로 **운영용 초기 SQL을 별도로 작성하고 검증한다.**

`organization_id`의 내부 조직 해석은 [Silo 검토안](./SILO_DB_ERD_REVIEW.md)의 제안이다. 실제 업무 범위와 BE의 인증·권한 처리를 확인한 뒤 명세에 반영한다.

## 5. AI 담당자 및 인프라·BE와 확인할 추가 기능

Extension은 PostgreSQL에 설치하는 추가 기능을 뜻한다. pgvector도 여기에 해당한다. **현재는 추가 기능의 목록과 버전을 확정하지 않는다.**

| 항목 | 현재 제안 | 확인할 내용 | 협의 대상 |
|---|---|---|---|
| **pgvector 사용 여부** | **검토 중** | AI 문서 검색용 벡터를 PostgreSQL에 저장할지, 다른 저장소를 사용할지 | AI·김민호·인프라 |
| **pgvector 버전·저장 구조** | 도입 결정 후 선정 | 선택한 AWS DB·엔진 버전의 지원 여부, 임베딩 모델·차원, 데이터량, 검색 속도, 고객사별 검색 격리 | AI·김민호·BE·인프라 |
| **pg_stat_statements** | 성능 분석용 후보 | 느린 쿼리 등의 실행 통계가 필요한지, 수집·접근·운영 설정 | 인프라·BE·김민호 |
| **pgaudit** | DB 작업 감사용 후보 | DB 구조·권한 변경 등을 어디까지 기록할지, 기존 업무 `audit_trail`과의 역할 및 로그 관리 | 인프라·BE·김민호 |

현재 72개 업무 테이블의 AI 영역은 생성 요청·결과·적용 이력을 다룬다. 벡터를 PostgreSQL에 저장하기로 하면 문서·청크·임베딩 관계를 추가 설계해야 한다. pgvector 검토가 진행 중이어도 기존 업무 테이블 설계는 계속할 수 있다.

추가 기능의 설치 가능 여부와 버전은 선택한 PostgreSQL 엔진 조합에서 확인한다. [AWS RDS PostgreSQL 확장 기능 지원 안내](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/PostgreSQL.Concepts.General.FeatureSupport.Extensions.html)
