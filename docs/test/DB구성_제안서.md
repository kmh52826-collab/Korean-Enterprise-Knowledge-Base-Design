# 데이터베이스 구성 및 인프라·BE 협의안

작성·취합: **김민호 · Database 담당**  
기준일: **2026-09-18**  
기준 문서: [테이블 명세서](../data-dictionary.md) · [Silo DB 구조 검토](./SILO_DB_ERD_REVIEW.md)

현재까지 논의한 방향과 담당자별 확인 사항을 정리한 문서입니다. **아래 선택지와 역할 분담은 협의안이며, 실제 구축 완료나 최종 승인을 의미하지 않습니다.**

## 1. 현재 정리된 방향

| 항목 | 현재 방향 | 남은 확인 |
|---|---|---|
| 언어·DB | **SQL / PostgreSQL** | 실제 사용할 엔진 세부 버전 |
| 회사별 분리 | **회사별 Silo DB** | 환경별 분리 범위와 신규 회사 생성 절차 |
| DEV 환경 | 프로젝트 방에 **RDS for PostgreSQL 구성안**이 제시됨 | DEV 채택 확정 여부. STG·PRD까지 확정된 것은 아님 |
| 운영 DB 서비스 | RDS for PostgreSQL 또는 Aurora PostgreSQL | 인프라에서 가용성·복구·비용을 같은 조건으로 비교 |
| 문자·시간 | **UTF8 문자 저장·UTC 시간 기준** 제안 | BE에서 날짜 자료형과 화면 표시 시간대 확인 |
| DB 변경 관리 | 변경 SQL을 파일로 보관하고 회사별 적용 이력 관리 | Flyway 채택 및 실행 담당·시점 |
| AI 벡터 검색 | **pgvector 미정** | AI·BE에서 검색 기능의 개발 범위부터 확인 |
| 파일 검사 | 업로드 검사 작업 `file_scan_job`은 명세에 반영 | 실제 검사 서비스·큐·처리 방식 |

RDS for PostgreSQL은 PostgreSQL을 AWS에서 관리형으로 운영하는 서비스입니다. 이용자가 적다는 정보만으로 서비스나 사양을 확정하지 않으며, **RDS가 항상 Aurora보다 저렴하다고 전제하지 않습니다.** [AWS RDS 설명](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_PostgreSQL.html)

## 2. Silo와 조직ID에서 결정할 내용

**이번 프로젝트의 회사별 Silo 전제는 회사마다 전용 DB 환경을 마련하는 것입니다.** 한 회사의 테이블을 각각 다른 서버에 나누는 뜻은 아닙니다.

| 구분 | A제약 | B제약 |
|---|---|---|
| DB 환경 | A제약 전용 DB 환경 | B제약 전용 DB 환경 |
| 테이블 | 현재 명세의 73개 테이블 한 벌 | 같은 구조의 73개 테이블 한 벌 |
| 저장 데이터 | A제약 사용자·프로젝트·문서·감사기록 등 | B제약 사용자·프로젝트·문서·감사기록 등 |

WEB/WAS나 Worker를 공유하더라도, **인증된 고객사에 맞는 DB로 연결**해야 합니다. DB 분리만으로 파일·검색·비동기 작업의 회사 구분까지 자동 해결되지는 않습니다.

### 먼저 업무 담당자에게 확인할 질문

> 검증 프로젝트는 회사 단위로만 등록하면 되나요? 아니면 ‘A제약 ○○공장 프로젝트’처럼 사업장을 지정할 수 있어야 하나요?  
> 또한 사용자·사용자 그룹·시스템도 어느 사업장 소속인지 관리해야 하나요?  
> 여기서 사업장은 QA팀·IT팀 같은 부서가 아니라 **A공장·B공장·연구소**를 뜻합니다.

| 답변 | ERD 검토 방향 |
|---|---|
| 회사 안의 사업장 구분이 전혀 필요 없음 | 사용자·그룹·시스템의 `organization_id` 제거 검토. 관련 FK·중복 방지 규칙·조회도 함께 수정하고 회사 기본정보의 보관 위치 결정 |
| 사용자·그룹·시스템의 사업장 소속이 필요함 | 해당 연결 유지. `organization`의 의미를 회사 내부 사업장 기준으로 정리 |
| 프로젝트 자체의 사업장 지정이나 사업장별 접근 제한도 필요함 | 프로젝트 소속 관계와 권한 규칙을 추가 검토 |

현재 `organization_id`를 참조하는 테이블은 **`app_user`, `user_group`, `system_asset`**입니다. 프로젝트에는 이 컬럼이 없으며, 연결된 시스템을 통해 그 시스템의 관리 조직을 조회합니다. 이것이 프로젝트의 사업장 소속을 직접 정의하는 것은 아닙니다.

**답변 전에는 조직ID를 일괄 삭제하거나 유지 확정하지 않습니다.** 기존 Silo 검토 문서의 본사·공장 예시는 내부 사업장 관리가 필요할 때의 예시입니다. `organization_type`은 ‘공장’ 같은 종류이므로 서로 다른 두 공장을 식별하는 ID를 대신할 수 없습니다.

## 3. 신규 고객사 DB 자동 생성은 이렇게 협의

‘회사별 DB 자동 프로비저닝’은 **신규 회사가 들어오면 DB 생성부터 사용 준비까지 정해진 절차로 자동 처리**하자는 요구입니다.

| 순서 | 준비할 내용 | 역할 분담 제안 |
|---|---|---|
| 1 | 신규 회사 식별자·환경을 정하고 전용 DB 자원, 네트워크·백업 설정 생성 | 인프라 |
| 2 | DB 접속 계정·비밀정보 준비, 실행 계정과 구조 변경 계정의 권한 구분 | 인프라 + BE |
| 3 | 테이블·제약조건과 승인된 초기 기준정보 적용 | DB 담당: 명세·기준정보 목록 / BE: 적용 SQL·실행 절차 |
| 4 | 회사와 DB 접속정보를 연결하고 로그인·Worker가 올바른 DB를 선택하도록 구성 | BE + 인프라 |
| 5 | 구조 버전·초기 데이터·회사 간 접근 차단을 확인한 뒤 사용 활성화 | BE + 인프라, DB 담당 검토 |

초기에는 **담당자가 실행 버튼이나 명령을 누르면 위 절차가 진행되는 방식**을 제안합니다. 고객 등록과 동시에 실행하는 완전 자동화는 도입 시점을 별도로 정합니다.

공동으로 정할 것은 **실행 주체, 완료 기준, 실패 시 복구·재시도 담당**입니다. 중간에 실패한 회사는 사용을 활성화하지 않고, 재실행해도 DB나 데이터가 중복 생성되지 않아야 합니다. 회사별 접속정보를 어디에서 관리할지도 정해야 하며, 현재 73개 업무 테이블에 그 관리 구조가 준비되어 있다고 가정하지 않습니다.

## 4. 인프라 담당자에게 확인할 사항

| 협의 항목 | 제시할 선택지·확인 요청 |
|---|---|
| 환경별 DB 구성 | **DEV의 RDS for PostgreSQL 채택 여부 확인**. STG·PRD도 같은 서비스인지, Aurora와 별도 비교할지 결정. 회사별 전용 인스턴스·클러스터 범위와 DEV 시험용 회사 구성도 명시 |
| 버전·용량·장애 대응 | 지원되는 PostgreSQL 세부 버전, 초기 용량, 단일 구성 또는 장애 대비 이중화 선택. 예상 회사 수·동시 사용량을 기준으로 산정 |
| 백업·보존 | 장애 시 **얼마 전 데이터까지 복구해야 하는지, 얼마나 빨리 복구해야 하는지** 확인 후 백업·복구 시험 계획 결정. 업무기록 보존기간은 업무·QA 담당과 별도 확인 |
| 자동 생성·접속 | 기존 인프라 코드 도구로 회사별 DB 생성 가능 여부, 접속정보 보관 방식, Private DB 접근 경로·암호화 연결·비밀정보 관리 방법 회신 |
| 파일 검사·AI 저장소 | 자체 검사 Worker 또는 관리형 검사 서비스 선택. 격리 저장 위치와 검사 결과 전달 방식 결정. pgvector 채택 시 엔진·확장 버전 지원 여부 확인 |

**DB 백업, S3 파일 보존, 업무 감사기록은 각각 대상이 다릅니다.** 파일 보존 설정만으로 DB의 승인 기록까지 보존되는 것으로 보지 않습니다.

## 5. BE 담당자에게 확인할 사항

| 협의 항목 | 제시할 선택지·확인 요청 |
|---|---|
| DB 초기화·변경 적용 | **Flyway 우선 검토 또는 팀 표준 도구 제안**. 별도 배포 작업으로 실행할지 앱 시작 때 실행할지 결정. 신규 회사 초기화와 기존 회사별 버전 업데이트 절차 포함 |
| 회사별 DB 연결 | 인증 정보에 따라 DB를 선택하는 방법, 회사별 접속정보 관리 위치와 연결 수 관리 확인. 화면에서 받은 회사ID만 믿고 DB를 선택하지 않도록 구성 |
| 조직ID·초기 데이터 | 2번의 업무 답변에 따라 수정 범위 확정. 역할·활동 등 공통 기준정보와 회사별 설정을 구분하고, 다른 회사 사용자·프로젝트 데이터를 복사하지 않도록 결정 |
| 파일·비동기 작업 | 검사 통과 및 파일 등록 전 사용 차단. 작업의 회사 식별, 중복 처리 방지, 실패·재시도 규칙 확인. AI·PDF 작업에도 필요한 항목이 있는지 별도 검토 |
| AI 검색 | AI 담당과 **현재 개발 범위**부터 확인. 벡터 검색 미사용 / PostgreSQL+pgvector / 별도 벡터 저장소 중 선택. 도입 시 문서·임베딩 저장 구조와 회사별 검색 범위를 별도 설계 |

파일 검사는 **검사 완료·위협 미검출·원본 동일성 확인·파일 등록**까지 마쳐야 업무에서 사용할 수 있습니다. 현재 AI 초안·결과 테이블이 있다는 이유로 검색용 벡터 구조나 모든 작업의 재시도 구조까지 갖춰졌다고 보지 않습니다. SQS 표준 큐는 같은 메시지가 다시 전달될 수 있으므로 중복 처리 방지가 필요합니다. [AWS SQS 설명](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/standard-queues-at-least-once-delivery.html)

### Git·Flyway는 어디에 쓰는가

- **Git:** 개발자가 만든 ‘최초 테이블 생성.sql’, ‘컬럼 추가.sql’ 같은 변경 파일과 수정 이력을 보관합니다. 팀의 코드 저장소에서 함께 관리할 수 있습니다.
- **Flyway:** 그 파일 중 해당 DB에 아직 적용하지 않은 변경을 실행하고 적용 이력을 기록합니다. 수동으로 실행한 모든 쿼리를 감시하는 도구가 아니며, AWS DB 서버 생성까지 담당하지 않습니다. [Flyway 공식 설명](https://documentation.red-gate.com/flyway/flyway-concepts/migrations)

현재 `erd/`의 14개 SQL은 그림별 참조 테이블이 중복된 **ERD 설명용 파일**입니다. 이를 그대로 합쳐 초기 DB를 만들지 않고, 테이블 명세를 기준으로 운영용 생성·변경 SQL을 준비해야 합니다.

## 6. 지금 전달하고 회신받을 순서

1. **김민호 → 업무 담당자:** 사업장 구분이 필요한지 2번 질문으로 확인합니다.
2. **김민호 → 인프라:** 4번 항목을 전달하고 DEV 채택 서비스·접속 조건·자동 생성 범위를 회신받습니다.
3. **김민호 → BE:** 최신 테이블 명세와 5번 항목을 전달하고 초기화·변경 적용·회사별 연결 방식을 회신받습니다.
4. **인프라·BE 공동:** 신규 회사 DB 준비의 실행 담당과 완료·실패 처리 기준을 합의합니다. 이후 DB 담당이 확정된 구조 변경을 명세·ERD에 반영합니다.

프로젝트 방에서 요청한 **Container Port, ALB 라우팅, Dockerfile·빌드 방식, 환경변수·Secret, 외부 API 통신 목록**은 BE가 관련 FE·AI 담당과 취합해 인프라에 전달해야 합니다. 김민호는 그중 **DB 초기 구조·기준정보·필요 확장**을 제공하고, 실제 접속값과 계정 발급은 인프라·BE가 연결해 확정하는 분담을 제안합니다.
