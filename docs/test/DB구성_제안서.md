# Validation Management Platform 데이터베이스 구성 제안 및 담당별 검토 요청

- 작성 기준일: **2026-09-18**
- 작성·취합: **김민호 — Database 담당**
- 기준 자료: [데이터 테이블 정의서](../data-dictionary.md), [회사별 Silo DB 검토안](./SILO_DB_ERD_REVIEW.md)
- 목적: 현재 설계 기준을 공유하고, 미정 항목은 **인프라와 BE 담당자에게 선택지를 제시하여 결정**한다.

## 1. 현재까지 정리된 내용

| 항목 | 정리 내용 | 상태 |
|---|---|---|
| DB·언어 | **PostgreSQL / SQL**을 기준으로 개발 | 확정 방향 |
| 고객사 분리 | **회사별 Silo**. 고객사별 전용 DB 서버 환경과 데이터베이스 구성 | 확정 전제 |
| 테이블 적용 범위 | 현재 **72개 업무 테이블 전체**를 회사별 DB에 동일한 구조로 구성하고 회사별 데이터 저장 | 설계 기준. 추가 요구에 따라 테이블 수는 변경 가능 |
| 이용자 규모 | 특정 업무 담당자가 사용하므로 이용자는 많지 않을 것으로 예상 | 정성적 정보. 회사 수·동시 접속·문서량·AI 검색량은 미확인 |
| 문자·시간 | **UTF8**로 문자 저장, **UTC**로 시간 저장, 화면은 사용자·사업장 시간대 적용 | DB 기준안. UTC는 기존 명세 기준 |
| 데이터 설계 | 기존 명세의 이름·자료형·관계·개정·전자서명·감사기록 원칙 유지 | 세부 제약과 구현은 BE와 검토 |
| AWS DB 서비스 | **RDS for PostgreSQL과 Aurora PostgreSQL을 비교 후 선정** | 미정. 어느 쪽이 더 저렴하거나 적합한지 검증 전 |
| DB 변경 관리 | SQL 파일의 수정 이력과 회사별 DB 적용 이력을 관리 | 관리 원칙 채택. Flyway 등 실행 도구는 미정 |
| pgvector | AI 검색 방식에 따라 사용 여부 결정 | 검토 중 |

Silo는 고객사별로 DB 환경을 한 벌씩 분리하는 방식이다. 회사 안의 72개 테이블을 각각 다른 서버에 두는 의미가 아니다. 회사별 테이블명·컬럼·관계와 DB 내부 스키마 이름은 동일하게 사용할 수 있다. 공유 DB 서버에서 DB나 스키마만 나누는 Bridge 방식은 이번 선정 후보에 포함하지 않는다.

김민호는 PostgreSQL·회사별 Silo라는 전제를 바탕으로 UTF8·UTC, 자료형·명명 규칙, 변경 이력 관리 원칙을 기준안으로 정리할 수 있다. **제품·도구·구체 버전·운영 수치는 아래 협의 결과로 확정한다.**

## 2. 선택 전에 구분할 용어

| 용어 | 의미 | 이번 결정과의 관계 |
|---|---|---|
| **RDS for PostgreSQL** | PostgreSQL을 AWS가 운영·관리하는 서비스 | AWS DB 서비스 선택지 A |
| **Aurora PostgreSQL** | AWS가 저장·복제 구조를 별도로 구성한 PostgreSQL 호환 DB 서비스 | AWS DB 서비스 선택지 B |
| **Git** | SQL 등 파일의 수정 전후 내용과 이력을 관리 | 변경 파일 관리. 파일이 보관되는 AWS 등의 장소와는 다른 개념 |
| **Flyway** | 변경 SQL 파일을 DB에 순서대로 실행하고 적용 이력을 기록 | DB 변경 관리 도구 후보. 모든 업무 SQL을 감시하는 로그 도구는 아님 |
| **업무 감사기록** | 사용자의 업무 데이터 변경·처리 내역 | 기존 `audit_trail` 등의 업무 구현 대상. Git·Flyway로 대체하지 않음 |
| **pgvector** | PostgreSQL에 벡터 자료형·거리 계산·검색 기능을 추가하는 확장 프로그램 | 기존 PostgreSQL에서 벡터 검색을 구현하는 선택지 |
| **별도 벡터 저장소** | 검색용 벡터를 별도의 DB·검색 서비스에서 관리 | pgvector와 비교할 수 있는 선택지 |

RDS와 Aurora는 둘 다 AWS의 관리형 서비스지만 저장·복제·장애 대응 방식과 지원 기능이 다르다. 비용만 비교하거나 이용자가 적다는 이유만으로 한쪽을 확정하지 않는다. [RDS 공식 설명](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/CHAP_PostgreSQL.html), [Aurora 공식 설명](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/CHAP_AuroraOverview.html)

Git은 파일 버전 관리, Flyway는 변경 파일의 DB 실행·이력 관리를 담당하므로 함께 사용할 수 있다. Flyway가 모든 회사 DB를 자동으로 찾아 실행하는 것은 아니며, 회사별 접속 대상과 배포 절차를 구성해야 한다. [Git 버전 관리](https://git-scm.com/book/en/v2/Getting-Started-About-Version-Control), [Flyway 변경 관리](https://documentation.red-gate.com/flyway/flyway-concepts/migrations)

## 3. 인프라 담당자에게 제시할 선택지

**인프라 담당자는 DB 서비스와 운영 구성의 검토를 주관한다.** BE는 호환성·예상 부하를, 김민호는 데이터 구조와 보존 요구를 제공한다. 실제 AWS 설정·비용은 아직 확인하지 않은 상태다.

| 번호·항목 | 제시할 선택지 | 선택 기준 | 회신 요청 |
|---|---|---|---|
| **I-01 AWS DB 서비스** | **A. RDS for PostgreSQL**<br>**B. Aurora PostgreSQL** | 같은 성능·백업·장애 대비 요구를 충족하는 구성으로 비용과 운영 부담 비교. 회사별 Silo 유지 | 선택 A/B, 추천 이유, 회사당·전체 예상 비용과 산정 조건 |
| **I-02 엔진 버전** | **A. PostgreSQL 17 계열의 지원 버전**<br>**B. 팀 표준 또는 다른 지원 계열** | 선택 서비스·리전의 지원 기간, BE 드라이버와 pgvector 등 필요한 확장의 호환성 | 계열·세부 버전, 지원 기간, 업데이트 방침. BE 호환성 확인 필요 |
| **I-03 장애 대비** | **A. 주 서버 중심 구성으로 시작**<br>**B. 다른 가용 영역에 장애전환용 서버를 추가** | A는 예비 서버 비용을 줄일 수 있지만 장애·복구 시 중단을 감수. B는 추가 비용으로 장애전환 대비. 선택 서비스에 맞게 구성 | 개발·검증·운영 각각의 선택, 장애 시 예상 중단·복구 절차 및 비용 |
| **I-04 백업 보관 기간** | **A. 7일 / B. 14일 / C. 35일 / D. 별도 기간 제안** | 숫자는 비교용 후보이며 확정값이 아님. 오삭제 발견 시점, 복구 요구, 선택 서비스의 지원 범위와 비용으로 결정 | 보관 일수, 특정 시점 복구 방식, 장기 보관·첨부파일 복구 방안 |
| **I-05 초기 사양·용량** | **A. 측정 부하를 충족하는 최소 사양 + 증설 기준**<br>**B. 예상 최대 부하와 여유 용량을 반영한 사양** | 회사 수·동시 사용자·문서 증가량·보고서·AI 검색 부하로 산정. 테이블 수나 이용자 수만으로 결정하지 않음 | 실제 인스턴스 사양, 저장 용량, 증설 조건, 월 비용 |
| **I-06 DB 관찰·감사 기능** | 성능 통계용 **pg_stat_statements 적용/미적용**<br>DB 작업 감사용 **pgaudit 적용/미적용** | 두 기능은 각각 결정. 필요한 통계·DB 관리 작업 기록, 지원 여부, 부하·로그 비용 확인. 미적용 시 필요한 관찰 수단 제시 | 기능별 사용 여부·버전, 수집 범위·보관 기간·확인 담당자 |

I-03의 A를 선택해도 자동 백업과 복구 절차는 필요하다. **이용자가 적다는 이유로 운영 환경의 장애 대비를 생략한다고 결정하지 않는다.** RDS의 주 서버 + 대기 서버 1대 방식에서 대기 서버는 일반 조회용 서버가 아니다. Aurora의 Reader와 역할을 동일하게 해석하지 않는다. [RDS 장애 대비 구성](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/Concepts.MultiAZSingleStandby.html)

I-04의 7·14·35일은 복구용 백업 후보이며, 승인 문서·전자서명·감사기록의 업무상 보존기간과는 별개다. 선택한 서비스의 보관 범위를 확인해야 한다. [RDS 백업 보관 기간](https://docs.aws.amazon.com/AmazonRDS/latest/UserGuide/USER_WorkingWithAutomatedBackups.BackupRetention.html)

다음은 선택지와 함께 인프라 담당자가 제시할 필수 구성 내용이다.

| 구성 항목 | 요청 내용 |
|---|---|
| 리전·Silo 배치 | 고객사별 전용 인스턴스 또는 클러스터 배치, 개발·검증·운영 분리, 신규 고객사 생성 절차 |
| 접속·암호화 | 허용된 서버의 접속 경로, 저장·통신 암호화, 자격증명·키 관리, 필요한 권한만 부여 |
| 유지보수·복구 | 업데이트 전 검증, 점검 시간, 장애 알림 담당, 회사별 복구 시험 및 파일 복구 연결 |

## 4. BE 담당자에게 제시할 선택지

**BE 담당자는 DB 연결·변경 적용·AI 연계 방식의 검토를 주관한다.** 배포 방법은 인프라와, AI 검색 방식은 AI 담당자와 공동 결정한다. 김민호는 테이블·관계·검증 조건을 정리한다.

| 번호·항목 | 제시할 선택지 | 선택 기준 | 회신 요청 |
|---|---|---|---|
| **B-01 DB 변경 관리 도구** | **A. Flyway**<br>**B. 팀에서 사용하는 다른 변경 관리 도구** | 팀 경험, 버전별 SQL 적용·이력 관리, 백엔드 호환성, 필요한 기능·라이선스·비용 | 선택 A/B. B는 도구명 명시. 버전·에디션, 선정 이유, 설정 담당자 |
| **B-02 변경 적용 시점** | **A. 배포 절차의 별도 DB 변경 단계**<br>**B. 애플리케이션 시작 시 실행** | A를 기본 제안. B는 회사별 접속·다중 인스턴스 기동·실패 처리·실행 권한을 통제할 수 있는지 확인 | 선택 A/B, SQL 작성·검토·실행 담당, 고객사 적용 순서·실패 처리 방법 |
| **B-03 감사 대응 AI 검색** | **A. PostgreSQL + pgvector**<br>**B. 별도 벡터 DB·검색 서비스**<br>**C. 벡터 검색 없이 DB 조회·키워드 검색·선택 자료 활용** | **AI 담당자와 공동 검토.** 실제 질문·문서로 검색 품질, 답변 근거, 속도·비용 비교. A/B도 정확한 업무 기록 조회와 병행 | 선택 A/B/C. A는 지원 버전·모델·벡터 차원·저장 구조, B는 제품·격리 방식, C는 지원할 질문 범위 |
| **B-04 회사별 DB 연결** | **A. 회사별 애플리케이션 실행 환경에서 전용 DB 연결**<br>**B. 공용 애플리케이션에서 인증된 회사에 따라 전용 DB 연결 선택** | 둘 다 DB Silo 유지 가능. 애플리케이션 배포 구조, 회사 수, 연결 관리·비동기 작업 중 혼선 방지로 결정 | 선택 A/B, 인프라와 합의한 연결 구조, 회사별 권한·배치·AI 작업 검증 방법 |

B-01은 Silo이기 때문에 Flyway가 필수라는 뜻이 아니다. 어떤 도구를 선택하든 **변경 파일 버전 관리와 회사별 DB 적용 이력 관리**를 충족해야 한다. 고객사 DB마다 다른 변경 단계가 존재할 수 있으므로 앱 버전과 DB 버전의 호환 방식도 정한다.

B-03에서 pgvector는 일반 PostgreSQL 테이블에 `vector` 컬럼을 만들고, 질문 벡터와 저장된 벡터를 비교하는 기능을 제공한다. 벡터는 임베딩 모델이 생성하고, 검색한 문서 내용은 프로그램이 LLM에 전달한다. pgvector 자체가 문서를 읽고 답변하는 AI는 아니다. [pgvector 공식 설명](https://github.com/pgvector/pgvector)

```text
벡터 검색을 선택한 경우
질문 → 임베딩 모델 → 질문 벡터
     → pgvector 또는 별도 검색 저장소에서 관련 문서 검색
     → 프로그램이 질문·문서 내용을 LLM에 전달 → 답변
```

산출물 초안 생성은 선택한 자료를 LLM에 전달하는 방식으로 시작할 수 있다. 감사 대응 AI도 벡터 검색이 무조건 필요한 것은 아니다. 승인자·승인일·시험 결과는 정확한 DB 조회로 확인하고, SOP·문서 본문의 검색은 B-03에서 정한다. 어떤 방식이든 회사·사용자 권한·문서 개정·근거 위치를 확인할 수 있어야 한다. 벡터 검색 결과는 정답이나 유효 승인본을 자동 보장하지 않는다.

다음은 선택 가능한 업무 정책이 아니라, BE가 기존 명세에 맞춰 구현·검증할 내용이다.

| 구현 항목 | 확인 요청 |
|---|---|
| 드라이버·자료형 | 선택한 DB 버전과 백엔드·연결 드라이버의 버전 조합, UUID·JSONB 등의 저장·조회 검증 |
| 문자·시간 | UTF8·UTC 및 화면 시간대 적용, 한글·영문 정렬·검색 규칙 제안 |
| 조직·권한 | `organization_id`를 내부 조직 식별용으로 유지하는 제안을 업무 범위와 대조. 고객사 DB 선택과 내부 조직 선택 구분 |
| 승인·개정·감사 | 중복 승인·개정 충돌 방지, 참조 대상 일치, 상태·서명·감사기록을 함께 확정하는 처리 |
| 운영용 스키마 | 72개 업무 테이블 명세를 바탕으로 초기 SQL과 변경 SQL 작성. ERD용 14개 파일을 그대로 합쳐 실행하지 않음 |

## 5. 결정 순서와 공동 확인 사항

김민호가 아래 정보를 취합해 두 담당자에게 제공한다. **인프라는 운영 구성을, BE는 개발·배포·연계 구성을 책임지고 검토하되 연결되는 항목은 공동 확인한다.**

| 먼저 확인할 정보 | 제공·확인 담당 | 영향을 받는 결정 |
|---|---|---|
| 예상 고객사 수, 회사당 동시 사용자·문서량·업무 처리량 | 김민호·업무 담당, BE가 처리량 검토 | I-01·I-05, B-04 |
| 허용 중단시간, 허용 데이터 손실, 기록 보존기간 | 업무 책임자, 인프라가 구현 가능성 검토 | I-03·I-04 |
| 감사 대응 AI의 질문 범위·자료·검색량 | AI·BE, 김민호가 업무 근거 확인 | B-03, I-01·I-02·I-05 |
| 기존 개발·Git 저장소·배포 도구 | BE·배포 담당 | B-01·B-02 |

1. **공통 기준 공유:** PostgreSQL, 회사별 Silo, UTF8·UTC, 기존 업무 명세를 기준으로 검토한다.
2. **후보 비교:** 인프라는 I 항목, BE는 B 항목을 검토하고 미확인 요구를 표시한다.
3. **공동 검증:** DB 서비스·버전·드라이버·확장 기능의 조합을 맞춘다. pgvector 채택 시 AI 담당자가 검색 품질을 검증한다.
4. **최종 결정 기록:** 김민호가 선택 결과·이유·남은 조건을 취합한다. 검증 환경에서 고객사 격리·변경 적용·복구를 확인한 후 운영에 반영한다.

## 6. 담당자 전달용 요청문과 회신 양식

### 인프라 담당자에게 전달

> PostgreSQL 및 회사별 Silo를 전제로 DB 구성을 검토하려고 합니다. 특정 업무 담당자가 사용하는 시스템이며 이용자는 많지 않을 것으로 예상하지만, 정확한 고객사 수와 부하는 추가 확인이 필요합니다.
>
> **3절 I-01~I-06의 선택지를 검토해 주세요.** RDS for PostgreSQL과 Aurora PostgreSQL은 동일한 성능·백업·장애 대비 조건으로 비교하고, 추천 구성·선정 이유·회사당 및 전체 비용·미확인 조건을 회신 부탁드립니다. 서비스·버전·추가 기능 호환성은 BE와 함께 확인해 주세요.

### BE 담당자에게 전달

> PostgreSQL, 회사별 Silo, UTF8·UTC를 기준으로 업무 DB를 설계하고 있습니다.
>
> **4절 B-01~B-04의 선택지를 검토해 주세요.** DB 변경 관리 도구, 적용 시점, 회사별 연결 방식을 선택하고 실제 드라이버 버전과 SQL 작성·배포 역할을 제안해 주세요. 감사 대응 AI는 AI 담당자와 함께 pgvector·별도 벡터 저장소·벡터 검색 없이 시작하는 안을 비교해 주세요. 선정 이유와 인프라에 필요한 조건도 함께 회신 부탁드립니다.
