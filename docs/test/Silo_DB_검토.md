# 회사별 Silo DB 전제의 ERD 정합성 검토 및 개선 제안

- 검토일: 2026-09-18
- 확정 전제: 고객사별 Silo DB 구성
- 검토 대상: [데이터 테이블 정의서](../data-dictionary.md), `erd` 폴더의 14개 SQL, [ERD 명세서](../erd-specifications.md), [전체 데이터 구조도](../erd-overview.md)
- 검토 범위: 72개 테이블·1,147개 컬럼의 명세와 ERD를 대상으로 한 구조·소속·권한 범위 검토. 실제 운영 DB의 배치 및 고객사 간 접근 차단 시험은 포함하지 않음

## 1. 검토 결론

**현재 테이블 관계에서 회사별 Silo DB와 충돌하여 반드시 삭제해야 하는 테이블·컬럼은 확인되지 않았다. 권고안은 기존 구조를 유지하면서 고객사 경계와 내부 조직의 의미를 구분하는 것이다.**

현재 `organization`에는 본사·공장·연구소·해외법인 유형이 정의되어 있다. 따라서 `organization_id`를 고객사 분리만을 위한 식별자로 보기는 어렵고, 고객사 내부의 운영 조직·사업장 소속을 나타내는 용도로 유지하는 것이 적합하다.

| 구분 | 권고 |
|---|---|
| 고객사 간 분리 | 고객사별 전용 DB와 인증·DB 연결 경계에서 보장 |
| 고객사 내부 조직 구분 | `organization`과 기존 `organization_id` 관계 유지 |
| 테이블·컬럼 수 | 권고안 적용 시 기존 72개 테이블·1,147개 컬럼 유지 가능 |
| 우선 보완 사항 | 고객사 DB 범위, 조직의 정의, 전역 권한의 범위, 공통 자료의 관리 범위를 명세에 명시 |
| 조건부 구조 변경 | 사업장별 접근 제한, 중앙 계정 공유, 중앙 자료 직접 참조 등의 추가 요구가 확정될 때 검토 |

Silo 배치에서는 동일한 업무 테이블 구조를 고객사별 DB에 각각 구성할 수 있다. `organization_id`의 존재 자체는 공유 DB 구조를 의미하지 않으며, 이 컬럼을 삭제하는 것만으로 Silo 격리가 구현되는 것도 아니다.

## 2. 현재 구조에서 확인한 사실

### 2.1 조직과 고객사의 의미가 혼용되어 있다

현재 [조직 정의](../data-dictionary.md#table-organization)는 다음 표현을 함께 사용한다.

| 항목 | 현재 명세의 표현 | 검토 결과 |
|---|---|---|
| 테이블 설명 | 고객사 또는 운영 조직 | 고객사 경계와 내부 운영 조직의 구분 필요 |
| `organization_code` | 조직/회사 식별 코드 | 어느 범위의 코드인지 설명 필요 |
| `organization_name` | 회사/사업장명 | 고객사명과 사업장명이 혼용됨 |
| `organization_type` | 본사·공장·연구소·해외법인 | 내부 조직·사업장 관리에 활용할 수 있는 구조가 이미 존재 |

`organization`에는 부모 조직을 참조하는 컬럼이 없으므로 현재는 **조직 유형을 가진 평면 목록**이다. 본사·공장·연구소를 등록할 수는 있지만, 상하위 조직 계층과 권한 상속까지 구현한 구조는 아니다.

### 2.2 `organization_id`를 직접 참조하는 업무 테이블은 3개다

조직 테이블 자신의 PK를 제외하면 직접 FK는 다음 세 개다.

| 테이블·컬럼 | 현재 용도 | 권고 |
|---|---|---|
| [`app_user.organization_id`](../data-dictionary.md#table-app_user) | 사용자 소속 | 해당 고객사 내부의 소속 조직으로 유지 |
| [`user_group.organization_id`](../data-dictionary.md#table-user_group) | 그룹 소속 | 해당 고객사 내부의 그룹 관리 조직으로 유지 |
| [`system_asset.organization_id`](../data-dictionary.md#table-system_asset) | 시스템·장비의 소속 | 해당 고객사 내부의 관리 조직·사업장으로 유지 |

프로젝트에는 `organization_id`가 없으며, 다음 경로로 검증 대상 시스템의 소속 조직을 확인할 수 있다.

```text
organization
  ├─ app_user
  ├─ user_group
  └─ system_asset
       └─ validation_project
            └─ 평가·시험·문서·일탈 등 프로젝트 업무
```

이 경로는 프로젝트의 검증 대상 소속을 설명한다. 프로젝트 참여자의 소속 조직이 반드시 시스템의 소속 조직과 같아야 한다는 뜻은 아니다.

### 2.3 ‘공통’·‘전역’의 고객사 범위가 명시되어 있지 않다

- `GLOBAL_ADMIN`은 ‘전체 관리자’, `group_role.scope_type`의 `GLOBAL`은 ‘전역’으로 설명되어 있다.
- 라이브러리·규정은 프로젝트 외 공용 자료로, 활동 선후행 조건은 전역 템플릿으로 설명되어 있다.
- 이 표현들이 고객사 내부의 공통 사용인지, 모든 고객사의 중앙 공유인지는 명시되어 있지 않다.

현재 FK는 이 테이블들을 같은 DB 안에 두고 사용하는 구조와 양립한다. 여러 고객사의 중앙 DB로 분리해야 한다고 정한 명세는 확인되지 않았다.

## 3. 권고하는 데이터 배치와 조직의 의미

**고객사 구분은 DB 경계에서, 내부 조직 구분은 `organization`에서 담당하도록 정의한다.**

```text
A고객사 전용 DB
  ├─ organization: A사 본사, A사 공장, A사 연구소
  ├─ 사용자·그룹·시스템·프로젝트
  ├─ 요구사항·설계·평가·시험·일탈
  └─ 문서·파일 정보·라이브러리·규정·승인·감사·AI 작업

B고객사 전용 DB
  ├─ organization: B사 본사, B사 공장
  └─ 동일한 업무 테이블 구조에 B사 데이터만 저장
```

이 안에서 A사의 조직 선택은 A사 DB 내부의 업무 소속을 선택하는 행위다. 다른 고객사의 DB로 전환하는 기능으로 사용하지 않는다.

회사와 연결할 DB를 식별하는 운영 정보는 인증·접속 설정 또는 별도 운영 관리 영역에서 관리한다. 그 식별자를 고객사 내부 조직의 `organization_id`와 같은 개념으로 취급하지 않는다. 이 때문에 72개 업무 테이블에 새로운 고객사 식별자를 일괄 추가할 필요는 없다.

현재 조직 유형 중 ‘해외법인’은 고객사와의 계약·격리 범위 안에 포함되는 운영 조직으로만 사용한다. 별도 고객사로 분리해야 하는 법인을 같은 DB의 조직으로 등록해서는 안 된다.

### 3.1 명세 문구 수정 제안

| 대상 | 제안 문구 또는 규칙 | 물리 구조 변경 |
|---|---|---|
| 문서 개요 | 본 명세는 한 고객사의 전용 DB 내부 데이터 모델이다. 동일한 업무 테이블 구조를 고객사별로 배치하며, 다른 고객사의 업무 데이터는 같은 DB에 저장하지 않는다. | 없음 |
| `organization` 설명 | 해당 고객사 내부의 운영 조직 및 사업장 정보를 관리한다. | 없음 |
| `organization_id` 설명 | 현재 고객사 DB 내 운영 조직·사업장을 식별하는 키. 고객사별 DB 선택에 사용하는 식별자가 아니다. | 없음 |
| `organization_code` | 고객사 DB 내에서 유일한 운영 조직·사업장 코드. | 없음 |
| `organization_name` | 운영 조직 또는 사업장명. | 없음 |
| `app_user.organization_id` | 사용자가 소속된 고객사 내부 조직. | 없음 |
| `user_group.organization_id` | 사용자 그룹을 관리하는 고객사 내부 조직. | 없음 |
| `system_asset.organization_id` | 시스템·장비를 관리하는 고객사 내부 조직 또는 사업장. | 없음 |
| `GLOBAL_ADMIN` | 해당 고객사 DB 범위의 전체 관리자. 다른 고객사 또는 서비스 운영사 전체의 관리 권한을 의미하지 않는다. | 기존 코드 유지 |
| `group_role.scope_type=GLOBAL` | 해당 고객사 DB 전체에 적용되는 그룹 역할 범위. | 기존 코드 유지 |
| 공용 자료·전역 조건 | 해당 고객사 DB 내 여러 업무·프로젝트에서 함께 사용하는 자료 또는 조건. | 없음 |
| 다형 참조·JSON 참조 검증 | 대상 유형·ID·개정은 현재 고객사 DB 안에서 해석하고, 기존의 부모·프로젝트·프로토콜 일치 검증을 함께 수행한다. | 설명·구현 규칙 보완 |

초기 고객사 DB에 사용자·그룹·시스템을 등록하려면 참조할 내부 조직이 먼저 있어야 한다. 최초 환경 구성 시 기본 운영 조직을 등록하는 절차를 포함한다.

### 3.2 기존 유일성 제약은 우선 유지한다

| 제약 | Silo에서의 의미 | 권고 |
|---|---|---|
| `organization_code` UNIQUE | 고객사 내부 조직 코드의 중복 방지 | 유지 |
| `app_user.email` UNIQUE | 해당 고객사 DB 내 계정 이메일의 중복 방지 | 유지. 서로 다른 고객사 DB의 동일 이메일 허용 여부와 로그인 방식은 인증 정책에서 정리 |
| `validation_project.project_code` UNIQUE | 해당 고객사 DB 내 프로젝트 코드의 중복 방지 | 유지 |
| 활성 그룹의 `(organization_id, group_code)` UNIQUE | 같은 내부 조직에서 같은 그룹 코드의 중복 방지 | 유지 |
| `(organization_id, management_number)` UNIQUE | 같은 내부 조직에서 같은 시스템 관리번호의 중복 방지 | 유지. 회사 전체 관리번호의 유일성이 필요할 때만 변경 검토 |

근거: [사용자](../data-dictionary.md#table-app_user), [사용자 그룹](../data-dictionary.md#table-user_group), [시스템](../data-dictionary.md#table-system_asset), [프로젝트](../data-dictionary.md#table-validation_project)의 컬럼·제약 정의.

### 3.3 내부 조직 간 협업은 고객사 간 접근과 구분한다

같은 고객사의 본사 QA 담당자가 권한을 받아 공장 프로젝트를 검토하는 업무는 Silo와 충돌하지 않는다. 고객사 내부의 그룹 참여와 프로젝트 참여는 기존 배정·권한 규칙으로 판단한다.

`user_group_member`나 `project_member`에 연결된 사용자와 그룹·프로젝트의 `organization_id`가 무조건 같아야 한다는 제약을 일괄 추가하지 않는다. 조직 소속이 다르다는 이유만으로 정당한 내부 협업을 차단할 수 있기 때문이다. 기존 프로젝트 데이터 간 소속 일치 검증은 그대로 유지한다.

반면 현재 `access_permission_grant`는 MENU/PROJECT 범위이고, `inventory_role_grant`에는 대상 조직을 지정하는 필드가 없다. 따라서 **`organization_id`가 있다는 것만으로 사업장별 인벤토리 접근 제한이 구현되어 있다고 볼 수 없다.** 이 기능이 필요하다면 별도의 업무 요구로 권한 범위를 설계해야 한다.

## 4. 공통 데이터와 기록의 관리 제안

기본안은 아래 데이터도 각 고객사 DB 내부에 두고 기존 참조 관계를 유지하는 것이다.

| 데이터 | 제안 | 검토 근거 |
|---|---|---|
| 역할·활동·선후행 조건 | 고객사별 기준정보로 관리. 프로젝트 생성 당시 채택한 조건 사본은 유지 | [`role`](../data-dictionary.md#table-role), [`validation_activity`](../data-dictionary.md#table-validation_activity), [`activity_dependency`](../data-dictionary.md#table-activity_dependency) |
| 기본 제공·사용자 지정 라이브러리 | 기본 자료를 고객사 DB에 적재하고 사용자 지정 자료와 함께 관리. 업무 항목은 로컬 라이브러리를 참조 | [`library_item`](../data-dictionary.md#table-library_item)의 BUILTIN/CUSTOM과 복사 후 독립 관리 규칙 |
| 공개 규정·가이드라인·내부 SOP | 사용할 문서판·조항을 고객사 DB에 보존. 내부 SOP는 해당 고객사의 자료로 관리 | [`regulatory_source`](../data-dictionary.md#table-regulatory_source), [`regulatory_clause`](../data-dictionary.md#table-regulatory_clause) 및 근거 연결 |
| Workflow·전자서명·감사기록 | 업무 기록과 같은 고객사 DB에 보관. 사용자와 서명 대상도 해당 DB 범위에서 해석 | [`workflow_instance`](../data-dictionary.md#table-workflow_instance), [`electronic_signature`](../data-dictionary.md#table-electronic_signature), [`audit_trail`](../data-dictionary.md#table-audit_trail) |
| 파일·증적 | 메타데이터는 고객사 DB에 보관. 실제 저장 객체의 회사별 접근 범위는 저장소·서버 설정에서 보장 | [`file_asset`](../data-dictionary.md#table-file_asset), [`evidence_link`](../data-dictionary.md#table-evidence_link) |
| AI 생성 요청·결과 | 작업과 결과를 해당 고객사 DB에 저장. 공용 작업 서버를 사용하더라도 실행 중 고객사 정보를 유지 | [`ai_generation_job`](../data-dictionary.md#table-ai_generation_job), [`ai_generation_result`](../data-dictionary.md#table-ai_generation_result), [`ai_result_item`](../data-dictionary.md#table-ai_result_item) |

기본 라이브러리와 공개 규정을 중앙에서 제작·배포하는 것은 가능하다. 다만 **자료의 중앙 배포와 업무 DB의 중앙 직접 참조는 구분한다.** 우선안은 필요한 자료를 고객사 DB에 적재해 기존 로컬 FK를 유지하는 방식이다. 배포 과정에서 고객사의 사용자 지정 자료나 과거 승인 근거를 덮어쓰지 않는다.

### 구조 변경이 필요한 조건

| 추가 요구 | 추가로 설계할 부분 | 현재 권고 |
|---|---|---|
| 자기 사업장 인벤토리만 조회·수정 | 조직 범위의 접근권한과 역할 적용 방식 | 요구가 확정될 때 구조 변경 검토 |
| 본사→사업장→부서 계층과 권한 상속 | 부모 조직 관계와 상속 규칙 | 현 조직 목록만으로 구현되었다고 보지 않으며, 필요할 때 추가 설계 |
| 모든 고객사가 하나의 중앙 계정을 사용 | 중앙 인증 계정과 고객사 내부 사용자·역할·서명자의 연결 | 현재 `app_user`를 그대로 중앙으로 옮기지 말고 별도 설계 |
| 고객 업무가 중앙 라이브러리·규정 DB를 직접 참조 | 기존 라이브러리·조항·사용자·파일 참조를 연결할 방식 | 로컬 적재를 우선 제안. 중앙 직접 참조가 확정되면 FK와 버전 보존 방식 재검토 |

이 항목들은 Silo 자체가 요구하는 테이블 변경이 아니다. 현재 문서만으로 추가 요구가 확정되었다고 판단하지 않는다.

## 5. 문서·구현에 반영할 우선순위

| 우선순위 | 대상 | 제안 작업 |
|---|---|---|
| 우선 반영 | `data-dictionary.md` | 한 고객사 전용 DB라는 전제, 내부 조직의 정의, 전역·공통 범위와 참조 검증 범위를 명확화 |
| 우선 반영 | `erd-specifications.md`·`erd-overview.md` | ‘고객사 전용 DB 내부 구조’라고 표시. 전체 도식의 기준정보·업무·공통 기능은 같은 고객사 DB 범위임을 설명 |
| 우선 반영 | 14개 ERD SQL의 안내·주석 | 동일 구조를 고객사별 DB에 구성하는 전제를 추가하고, 고객사/내부 조직을 혼용한 주석을 정리. 권고안에서는 PK·FK·UNIQUE 변경 없음 |
| 구현 단계 확인 | 인증·DB 연결·비동기 작업 | 인증된 고객사 정보로 DB를 결정. 조직 선택값이나 요청에 전달된 임의 식별자만으로 다른 고객사 DB를 선택하지 않도록 처리 |
| 운영 단계 확인 | 파일·검색·백업·배포 | 회사별 파일 접근과 검색 범위, 백업·복구 대상, 고객사별 스키마 버전 적용 절차 확인 |

`file_asset.uploader_id`는 시스템 생성 파일에서 NULL일 수 있고, AI 작업의 프로젝트·요청자도 조건에 따라 비어 있을 수 있다. 고객사를 업로더나 프로젝트 ID만으로 추론하지 말고, 서버가 검증한 고객사 실행 정보로 결정해야 한다.

현재 72개 테이블에는 RAG 문서 청크·임베딩 저장 구조가 정의되어 있지 않다. AI 검색의 실제 고객사 격리는 AI 저장소·검색 설계에서 확인할 항목이며, 이를 이유로 이번 검토에서 벡터 테이블을 임의 추가하지 않는다.

고객사별 DB의 연결 정보, 백업·복구와 스키마 배포는 운영 설계 사항이다. 관련 테이블이 72개 업무 명세에 없다는 이유만으로 ERD 결함이라고 판단하지 않는다. 기존 14개 SQL도 ERD용 정의이므로, 고객사 DB 초기화·변경 적용을 위한 운영 마이그레이션은 별도로 구성해야 한다.

| 다른 고객사의 파일 경로나 검색 대상을 직접 지정 | 다른 고객사의 파일 다운로드·검색 결과 접근 차단 |

## 7. 보고용 요약

> 회사별 Silo DB를 확정 전제로 현재 72개 테이블과 14개 ERD를 검토했습니다. `organization_id`는 사용자·그룹·시스템의 세 테이블에서 직접 참조하며, 본사·공장·연구소 등 고객사 내부 조직을 구분하는 용도로 유지할 수 있습니다. 따라서 현 단계에서 테이블·컬럼·FK의 일괄 변경은 권고하지 않습니다. 고객사 분리는 전용 DB와 인증·접속 경계에서 보장하고, 명세의 고객사/조직 혼용 및 전역·공통 범위를 우선 정리하는 안을 제안합니다. 사업장별 접근 제한이나 중앙 계정·자료 공유가 추가로 요구되는 경우에는 해당 부분에 한해 구조 변경을 별도 검토해야 합니다.
